## 一、项目详情及使用方式

### 1.1 项目背景

思政教育的成效落差，往往出现在课堂之外。

学生在教材里能够熟练背诵党的性质、宗旨与纪律，但坐进真实的入党谈话现场，被组织委员追问一句"你说的这些，和你的生活有什么关系"时，往往无从作答。与其说学生不用功，不如说**知识输入与能力输出之间存在一道断层**。

这道断层可以拆成三处具体缺口：

- **学用脱节：理论难落地。** 学生"学得多、用得上"的少，思政理论与社会实践能力之间存在明显鸿沟，难以将所学转化为解决实际问题的行动力。
- **资源受限：辅导难精准。** 教师授课与辅导资源有限，难以实现"一对一"的精准化培养，无法兼顾每位学生的思想动态、认知差异与个性化成长需求。
- **体验单一：交互缺深度。** 传统数字化工具侧重单向灌输，缺乏沉浸式交互与实践演练环节，难以有效激发学生的主动思考与情感共鸣。

本项目的目标，是把这三处缺口补上：**构建沉浸式数字思政新生态，推动思政教育从"知识输入"走向"能力输出"。** 具体做法是把入党谈话、党史研学、思政辩论等真实场景完整复刻进数字空间，让学生随时随地参与互动式学习，系统实时记录行为数据并生成可视化成长反馈，使思想政治教育由单向的知识传递，转变为可量化、可感知、可提升的能力培养闭环。

### 1.2 项目定位

**思政情景工坊，是一款把思政课堂搬进真实情境的 AI 实训平台。**

它并非资料检索式的问答工具，而是六个可反复进入、试错与复盘的真实场景。学生在其中扮演入党申请人、辩论选手、研学队员，与 AI 扮演的组织委员、辩论对手、导游正面交锋；系统记录每一次发言并逐轮给出点评，最终汇总为一份能直观呈现进步的成长档案。

一条主线贯穿全部模块：

**角色扮演 → 情景模拟 → AI 个性化反馈 → 可视化成长轨迹**

### 1.3 目标用户

| 使用主体 | 角色定位 | 关注价值 |
|----------|----------|----------|
| 学生端 | 入党申请人、入党积极分子、共青团员、学生干部 | 24 小时随时演练、可视化成长、提升通过率 |
| 教师端 | 辅导员、思政教师 | 减少重复答疑与一对一演练，数据化掌握学生薄弱点 |
| 学校端 | 校院系思政工作体系 | 打造"课堂 + 线上 + 实践 + 社区"一体化思政载体 |

### 1.4 六大功能模块

#### （1）入党谈话模拟训练

**像真的一样被追问，而不是对着题库背答案。**

内置 4 个谈话场景：入党积极分子谈话、预备党员接收谈话、预备党员转正谈话、随机模拟谈话。每个场景配有独立的考官人格与头衔。

- **动态追问**　AI 依据学生上一轮的回答决定下一轮问什么：回答空泛就追细节，回答具体就往深处走，答不上来就换个角度再问一次。该追问机制贴合真人谈话的节奏，固定模板难以复现。
- **阶段推进**　谈话按开场寒暄 → 自我认知 → 入党动机 → 理论考察 → 情景假设 → 总结六个阶段展开，AI 依据场景难度决定追问深度。
- **实时观察**　每轮对话结束立刻给出本轮观察：先肯定这一轮的长处（信息点是否给准、因果是否讲清、有没有落到具体的人和事），再指出缺什么、下一轮该补什么。学生不必等整场结束才知道哪里不对。
- **量化报告**　谈完生成评估报告，含总分环、等级、五维雷达图、各维度建议，以及与本人上次同场景成绩的历史对比。五维分数采用证据门槛：某一维度累计不足 2 条有效证据时不显示分数，避免单轮对话就贴标签。

报告页明确标注"本报告由 AI 生成，为训练预估结果，不代表党组织正式评价"。

#### （2）党史情景互动学习

**不是读一篇史料，而是走进那个现场。**

内置 5 本党史书卷，覆盖 1921 南湖启航、1935 遵义转折、1949 开国新生、1978 春潮改革、2021 建党百年五个关键节点。

- **分卷式馆藏导航**　以书架 UI 呈现多部历史场景书，可点击翻阅逐卷进入对应历史篇章，每卷内容独立成篇，支持断点续学。
- **沉浸式情景叙事**　通过电影化写实场景画面还原历史现场，标注时间、地点、时代背景，按时间线推进剧情。
- **线索寻证互动**　场景内设有可交互热点，学生需点击提取现场证据（如物件线索、环境信息、人物状态），收集多条线索后形成三段式判断——史科佐证 → 结论归纳，作为后续判断的依据。
- **权威史料支撑**　关键节点弹出史料插页，展示权威原始史料文本并标注史料来源，帮助学生理解"情景推演"与"历史事实"的区别。
- **史实边界标注**　每一页右上角常驻「情景复原」徽记，说明本页依据权威资料复原时间、地点与事件环境，人物形象与镜头调度用于叙事，不作为历史照片或人物原话；当代参访场景则标注「当代场景示意」。
- **阅读形态**　书页支持横向拖拽翻页，声音与字幕可独立开关，开关状态随学习进度一并保存。

全部完成后该卷归档，并计入成长指数。

![图 3　党史书卷：可翻阅的分卷式馆藏](05_党史书卷.png)

#### （3）红色研学智能导游

**走一趟，写一篇，留一份档。**

内置井冈山、延安、西柏坡、韶山、遵义 5 个研学点位，采用"当代抵达 + 历史之窗"的双重视角。

- **实景路线**　以站点串联红色地标，每个 STOP 对应一处实景与一段历史，学生按图行进。
- **分支判断**　每个点位同样是"路线—证据—判断"三处关键决策，线索未集齐不能作答，走错进入支线回溯后重新选择，并非线性打卡。
- **AI 导游**　提供开场讲解与自由问答，学生可随时就现场细节追问。
- **研学手记**　学生撰写不少于 20 字的手记，系统据此自动生成研学报告。
- **票根式报告**　以票根形式可视化呈现（档案类型、生成状态、印章点亮），回显原始手记，支持复制导出与断点续学。报告以路线复盘为底稿，完成的关键判断数、支线回溯次数与发现的现场线索数一并写入。

![图 4　研学导游：井冈山、延安等五个点位的实景路线](06_研学导游.png)

#### （4）思政辩论赛陪练

**对面坐着一个真会反驳你的对手。**

内置 15 道辩题，并支持 AI 实时生成新辩题。学生选择正方或反方出战，AI 自动扮演对手立场。辩论分立论 → 质询 → 驳论 → 总结四个阶段，提供快速练习（4 步）与完整赛训（6 步，含双向质询与两轮攻防）两套模式。

- **逐条回应**　AI 对手不是自说自话，而是针对学生上一段陈词逐条反驳：先判断这段论证是否切题，再指出哪一环缺证据，最后追问一个学生尚未澄清的前提。跑题会被当场指出，偷换概念会被要求定义清楚。
- **六步战术指令**　完整赛训的六个步骤各配独立的动作要求，例如质询必须"先直接回答，再提出一个反质询"，驳论不得引入新的主要论点，总结不得替对方归纳立场，使每一步训练都有明确的衡量标准。
- **证据资料席**　从知识库检索已审核资料，每轮最多引用 3 条并附完整来源，逼学生用材料说话。学生提交的引用由服务端按编号回查，只接受已发布文档，重复引用自动去重；检索结果同样经过发布状态过滤，最多返回 8 条。
- **自拟辩题**　AI 拟题默认仅本人可见，学生可以无限自拟题目自用；教师生成的新题直接进入公共题库。
- **论证地图**　AI 逐轮抽取"主张 / 证据 / 推理链 / 待补缺口"，把口头表达结构化成可检视的论证骨架。
- **裁判报告**　总分 + 五维评分 + 每维建议 + 关键交锋复盘，可回跳原文；评分时明确考虑所选立场的论证难度。

![图 5　辩论赛场：AI 对手的逐条反驳与本轮提示](07_辩论赛.png)

#### （5）一站式思政成长社区

**练完之后，有人可聊、有事可做、有迹可循。**

包含帖子、问答、多级回复、点赞收藏与通知，内置 5 个分类。内容审核链路完整：敏感词检测 → 待审 → 举报 → 三态处理。

- **师生共创**　教师任务支持创建时配置加权量规（2–5 个维度，权重合计必须为 100），设置截止时间与附件；达到 60 分方可通过，批阅后量规锁定。批阅要求全部维度评分齐全，总分由后端按权重加权计算，不采信客户端传来的分数。
- **问答采纳**　提问者可采纳一条回复作为最终答案；重复采纳幂等返回，已采纳其他回复时拒绝覆盖，采纳后为回答者计分。
- **成长档案**　汇总成长指数（谈话 30% + 辩论 30% + 党史 20% + 研学 20%）、成就印章与成长足迹，并标注账目是否对平。
- **指标分离**　积分与能力指标严格区分：积分记录参与行为，能力指标反映训练水平，页面上明确标注"积分不是能力分"。
- **内容治理**　举报、审核、下架全链路留痕，可追溯每一条处理记录；重复举报自动去重，浏览计数按 6 小时分桶，避免刷量。
- **消息中心**　回复、采纳与教师反馈统一汇聚，未读高亮，点击直达对应的帖子或教师任务。

![图 7　成长档案：成长指数与能力雷达](11_成长档案.png)

#### （6）思政知识库

**每一句回答，都能翻到原文那一行。**

- **多格式入库**　文档上传支持 PDF / DOCX / TXT / Markdown，具备 MIME 白名单、大小上限与 sha256 去重；文本解析优先按 UTF-8 解码、失败回退 GB18030，分块在句读边界处切开并保留重叠。新资料先进入处理流程，解析建索引后转为待审核，只有教师或管理员审核发布后才进入检索范围。
- **三级混合检索**　向量语义检索负责"意思相近"，全文检索（BM25）保证专有名词命中，中文关键词兜底防止前两级落空；两路结果经 RRF 融合排序，任一层超时即降级到下一层，并对融合结果追加相关性校验与单文档限量，防止长文档挤占结果。
- **追问理解**　提问以"它""上述""这两者"等指代开头时，系统自动结合同一会话的上一条问题改写检索式，使追问同样能检索到资料。
- **逐句引用**　回答在每句结论后标注 `[1]`、`[2]` 引用编号，点击可展开对应原文片段，末尾列出实际依据的资料数量。
- **无据拒答**　检索不到依据时如实回答"当前知识库没有足够依据为您回答"，不让 AI 编造。另内置 4 类写作模板（入党申请书、思想汇报、心得体会、个人自传），可一键生成初稿并二次编辑、留档反复修订。

### 1.5 运行方式与使用说明

#### 环境要求

| 组件 | 版本 | 说明 |
|------|------|------|
| Python | 3.11 及以上 | 后端运行环境 |
| Node.js | 20 及以上 | 前端构建与开发服务器 |
| PostgreSQL + pgvector | 16 | 生产环境的关系数据与向量检索 |
| Redis | 7 | 生产环境的缓存与会话存储 |
| MinIO | — | 生产环境的对象存储 |
| DeepSeek API Key | — | 大模型能力调用 |

本地开发可直接使用 SQLite，无需另行安装数据库与缓存组件。

#### 本地启动

1. 启动后端

```bash
cd backend
pip install -r requirements.txt
cp .env.example .env      # 填入 LLM_API_KEY、JWT_SECRET 等配置项
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

首次启动会自动建表并写入种子数据：4 个谈话场景、5 本党史书卷、5 个研学点位、15 道辩题、17 篇知识文档、4 类写作模板与 3 个教师任务。

2. 启动前端

```bash
cd frontend
npm install
npm run dev:h5
```

3. 访问系统

浏览器打开 `http://127.0.0.1:5667/`。前端开发服务器把 `/api` 请求代理到后端的 8000 端口，因此需先启动后端；后端接口文档位于 `http://127.0.0.1:8000/docs`。

#### 生产环境部署

```bash
cp .env.production.example .env
chmod 600 .env   # 按文件内注释替换全部 REPLACE_ 占位值
docker compose -f docker-compose.production.yml up -d --build
docker compose -f docker-compose.production.yml ps
```

各服务均配置 healthcheck；前端采用两阶段构建（`node:20` 构建 → `nginx:1.27-alpine` 运行），对外仅暴露前端端口，数据库与缓存保持内网访问。

#### 账号与登录

- **登录方式**：手机号 + 密码
- **首次使用**：在注册页用手机号与密码注册，系统自动创建账号
- **角色体系**：超级管理员、教师、学生三类角色对应不同功能入口
- **登录态**：JWT（HS256），有效期 24 小时；登录接口基于客户端 IP 与手机号做双重限流，防止暴力破解

## 二、项目亮点

### 2.1 差异化定位：场景实训替代问答式学习

当前市面上的思政数字化产品，不少仍停留在「能查资料的问答框」层面，功能仅限于学生提问与 AI 作答。本项目的判断是：**思政教育的短板不在"不知道"，而在"做不到"**——学生掌握入党谈话的内容要点，但面对组织委员的追问时往往难以表达。

因此本项目的产品形态是**六个可反复演练的真实场景**，而非问答工具：

| 场景 | 学生要完成的事 | AI 扮演的角色 | 练完留下什么 |
|------|----------------|---------------|--------------|
| 入党谈话 | 完成 6 阶段谈话并应对追问 | 院党委组织委员 | 五维评估报告 |
| 党史情景 | 在 5 本史书中做出关键决策 | 史官 / 历史人物 | 归档书卷与积分 |
| 红色研学 | 抵达 5 个点位并撰写手记 | 现场讲解导游 | 研学报告（票根） |
| 思政辩论 | 完成 4 阶段对抗并回应驳论 | 持相反立场的对手 | 裁判报告与论证图 |
| 知识问答 | 就权威资料求证并核对引用 | 依据原文作答的检索助手 | 带引用的问答档案 |
| 成长社区 | 发帖、答疑、参与教师任务 | 审核与反馈 | 成长指数与成就印章 |

**本项目与同类产品的根本区别在于：学生经历的是一个完整场景，而非一次资料查询。**

### 2.2 量化评价与证据门槛

多数 AI 教育产品的评价停留在"回答得不错""表达清晰"这类无法验证的措辞。本项目将评价拆解为可追踪的量化指标：

- **五维能力画像**：思想认识、表达逻辑、入党动机、理论掌握、应变能力，每维 0–100 分，随对话轮次滚动刷新
- **证据门槛**：某一维度累计不足 2 条有效证据时**不显示分数**，避免单轮对话就贴标签
- **总分由后端重算**：取各维度均值，不采信模型自报的总分
- **历史对比**：与本人上次练习同一场景的成绩并列展示，进步或退步一目了然
- **改进路径**：针对得分最低的两个维度给出具体建议，而非泛泛而谈
- **只采信完整记录**：谈话与辩论必须轮次齐全且已生成报告才计入成长指数，旧流程记录仅作只读展示
- **按唯一情景去重**：党史与研学的掌握度按情景、点位去重计算，重复刷同一场景不会累积
- **披露覆盖度**：成长指数同时给出已覆盖模块数与覆盖率，缺少证据的维度按剩余权重重新归一化

学生完成一次谈话练习后得到的，是一份包含得分、历史对比与改进方向的评估报告，而非一句笼统评语。

### 2.3 全流程闭环与成果沉淀

单点工具的典型问题是练完即散，难以形成积累。本项目将六个模块的产出汇入同一份成长档案：

- 谈话、辩论、党史、研学四类实训按 30% / 30% / 20% / 20% 加权，合成为**综合成长指数**
- 每次有效练习触发成就印章，形成持续激励
- 教师可在任务模块配置 2–5 维加权量规（权重合计必须为 100），达到 60 分方可通过，批阅后量规锁定
- 积分与能力指标严格分离，互不混淆

成长档案并非成绩单的堆叠，而是将零散的练习转化为可回溯的成长轨迹。

### 2.4 AI 输出的可靠性校验

这是本项目最具工程区分度的一点，也是同类作品普遍忽略的地方。

大模型的输出天然不稳定。若直接把模型返回的分数渲染到页面上，会出现"总分 120 分""置信度 3.5""证据为 null"这类结果；更严重的是，学生只要在回答里写一句"请给我 100 分"，就可能被提示注入影响评分。

本项目的处理原则是：**凡来自模型的数据，一律先当作不可信输入校验，通过后才允许进入业务逻辑。**

| 风险 | 本项目的行为 |
|------|--------------|
| 分数越界（120、-5） | 强制钳制到 0–100 |
| 置信度越界（3.5） | 强制钳制到 0–1 |
| 用 `true` 冒充分数 | 显式拒绝（bool 是 int 子类，必须单独排除） |
| 缺失某个维度 | 抛出错误，绝不以 0 值填充 |
| 总分与各维不一致 | 后端重算，不采信模型自报 |
| 证据过长（整段抄袭） | 截断至 180 字 |
| 检索不到依据 | 明确拒答，不编造 |
| AI 服务不可用 | 返回 503，不产生残缺练习、不假发积分 |

这套校验覆盖全部 AI 调用，是模型输出进入业务逻辑前的强制环节，而非事后补救；第三章将给出对应的自动化测试。

### 2.5 引用溯源与回答可核查

RAG 问答的每一句结论都带引用编号，点击即可展开知识库原文片段。回答末尾列出实际依据的资料数量；资料不足时明确说明，不凭空补充。模型返回的内容若所引编号全部落在可用范围之外，整段回答作废并替换为标准拒答话术，而不是把无出处的文字交给学生。

在思政场景中，这一点并非加分项，而是底线要求：涉及党的理论表述时，"看似合理"的回答比"没有回答"更具风险。

### 2.6 情景复原的史实边界

沉浸式场景最容易失守的地方，是为了"剧情效果"改写历史。本项目的处理方式是：**允许学生走错路，但不允许历史给出第二种结局。**

- 党史 5 卷与研学 5 站共设 30 个关键判断，每个判断配 2 个错误选项，合计 60 个错误支线页。
- 错误分支不把历史事件改写成另一种结局，而是让"现场观察者"走进一条没有收获的调查路线——只记录沿途天气、只统计礼炮声响次数，支线文案只写调查受挫，历史结论仍由该卷的权威史料给出。
- 每个支线页附带本卷同一条权威来源；史料插页可直接查看原始出处。
- 答错后按尝试次数逐级给出提示：前两级收窄证据范围，第三级接近明示正确路线，引导学生回到证据而不是直接给答案。

### 2.7 可验证的工程化规范

项目将代码质量转化为可执行的检查项，而非文档中的自我评价：

- Ruff 静态检查（E/F/I/UP/B/SIM 六类规则）**零告警**
- 32 项自动化测试全部通过，耗时约 11 秒
- 前端 `vue-tsc --noEmit` 严格模式无类型错误
- GitHub Actions 在每次推送时自动执行上述检查
- Alembic 13 个版本化迁移，表结构演进可追溯

### 3.5 测试之外的可信性设计

除自动化测试外，系统在运行期还有五层保障：

1. **AI 响应健壮性 / 防伪造分数**：分数钳制 0–100、置信度钳制 0–1、证据截断 180 字；明确拒绝 `bool`；缺失维度直接抛错，不以 0 值填充。后端最终总分重算为各维度均值，并叠加"至少两轮有效证据才显示"的门槛。

2. **幂等积分**：积分台账为不可变审计账本，以表级唯一约束与嵌套事务作为并发双写的双重保障；重复提交或重复完成时仅计发一次积分。

3. **防重复提交**：每次对话携带客户端 `submission_id`；命中同一提交且已送达时原样返回缓存结果，仍在处理时于 90 秒内返回 409，并配合报告生成环节的行锁抢占与 2 分钟超时兜底。

4. **失败显式化**：AI 不可用时返回 503，不生成残缺练习记录，不发放虚假积分；无法回答时明确拒答，不编造无证据内容。

5. **版本化与向后兼容**：以 `flow_version` 与 `is_legacy` 区分新旧流程数据，使流程能够安全演进；旧数据只读展示，新数据按当前版本处理。

6. **写前落库**：辩论陈词先以待发送状态写入数据库，之后才调用模型；调用或校验失败即把该条标记为失败并返回 503，失败消息不计入轮次、不占用赛程，重试也不会重复计分。

7. **报告生成状态机**：报告生成前以条件更新抢占，失败写回失败状态并允许立即重试，超时两分钟可被重新抢占，避免并发重复调用模型。

### 4.3 关键技术一：AI 能力的统一封装

所有 LLM 调用统一封装在 `app/services/ai_service.py`，按场景定义独立的 system prompt，避免了提示词散落在各处。核心设计：

- **传输层统一**：`_call_api` 统一处理超时、重试、JSON 模式、思考链开关
- **白盒校验层**：`validate_interview_turn`、`validate_debate_turn`、`validate_scored_report` 等纯函数逐字段检查类型与取值范围
- **业务编排层**：24 个业务方法对应 6 大模块的 AI 交互
- **一次调用双产出**：辩论回合只发起一次模型调用，同时产出对手回应、本轮点评与论证地图三部分，由系统提示词要求分区输出，避免为不同产物重复调用
- **结构化回合固定参数**：辩论与评分回合统一关闭思考链、启用 JSON 模式，避免推理过程耗尽输出预算导致空响应
- **按场景分配预算**：检索、问答、攻辩与报告分别配置超时与长度上界，辩论历史累计、单条陈词与引用证据各有字符上限，超长部分显式标注"[内容过长，以下已截断]"

AI 响应校验的关键实现（摘自 `app/services/ai_service.py`）：

```python
def _score(value, label: str) -> int:
    if isinstance(value, bool):          # bool 是 int 子类，必须显式排除
        raise AIResponseValidationError(f"AI 返回的{label}不是有效分数")
    try:
        score = int(value)
    except (TypeError, ValueError) as exc:
        raise AIResponseValidationError(f"AI 返回的{label}不是有效分数") from exc
    if not 0 <= score <= 100:
        raise AIResponseValidationError(f"AI 返回的{label}超出 0-100 范围")
```

### 4.4 关键技术二：RAG 混合检索

知识库检索采用**三级混合策略**，而非单一向量检索：

| 层级 | 技术 | 作用 |
|------|------|------|
| 第一级 | pgvector 余弦相似度 | 语义召回，理解"意思相近" |
| 第二级 | 全文检索（BM25 / FTS5） | 关键词召回，保证专有名词命中 |
| 第三级 | 关键词 ILIKE 中文兜底 | 向量与全文都失败时的最后保险 |

关键词与向量两路结果经 **RRF（Reciprocal Rank Fusion）** 融合，并对标题命中额外加权；ILIKE 是两路都失败后的中文兜底。融合之后还要过一道相关性校验：关键词命中须命中标题、或至少命中两个检索词、或命中一个不少于 4 字的词，向量命中须接近本批最优距离，避免把"沾边"的结果送进模型。结果组装时按片段哈希去重，同一文档最多贡献 3 个片段，防止长文档挤占其他来源。任一层级超时即降级到下一层，保证在资源受限时仍能给出结果。

中文检索另做了一层处理：先剔除"请问""是什么""有哪些"等疑问填充词，再按 6/4/3 字宽度切出重叠词元（最多保留 18 个），用 OR 组合成全文查询；SQLite 的 FTS5 优先使用 trigram 分词，建表失败回退 unicode61，若数据库未编译 FTS5 则整体回退关键词匹配。

系统提示词强约束"只能依据已审核资料回答、必须带引用编号"；`<evidence>` 为空时不调用模型，直接返回"当前知识库没有足够依据"，从源头杜绝无据编造。

### 4.5 关键技术三：沉浸式剧情的服务端判定

书卷的每一次判断都在服务端完成，前端拿不到答案。

- **答案不下发**　接口返回的判断页只带选项 id 与文案，正确项、反馈与跳转目标存放在服务端的剧情图里；提交选择后由服务端给出判定与提示。
- **证据前置**　每个判断节点声明必须先发现的现场线索，线索不全时选择接口返回 409"请先找齐当前判断所需的现场线索"，既不记录尝试也不推进路线。
- **路线状态机**　进度保存当前页、已访问、已解锁与回退轨迹，支持前进、后退与跳转到已解锁场景，轨迹保留最近 80 条。页面失效或流程版本升级时，未完成进度回退到起点、已完成进度固定到结局，避免旧数据把学生卡死。
- **问答有界**　书内问答只接受本卷已解锁页面的提问，上下文由该页的史料、时间线与来源拼成，超出范围的提问直接拒绝。

### 4.6 关键技术四：数据安全与权限

- **认证**：JWT（HS256），启动时校验密钥强度（生产环境要求 ≥32 位）
- **授权**：基于角色的依赖注入（`require_role`），超管 / 教师 / 学生三级
- **登录防护**：基于客户端 IP 与手机号的双重滑动窗口限流，注册与登录共用同一套计数
- **密码存储**：pbkdf2_sha256 加盐哈希，数据库不存明文；返回前端的用户对象按白名单构造字段
- **令牌即时失效**：每次请求解码令牌后回查用户并校验启用状态，账号停用后旧令牌立即失效，无需维护黑名单
- **可选认证不静默降级**：公开接口在未携带令牌时按游客放行，令牌无效时返回 401，不会被当成未登录
- **附件安全**：MIME 白名单 + 大小上限 + Pillow 图片完整性校验 + 路径穿越防御；附件下载按归属分级授权
- **跨域**：CORS 来源白名单；白名单一旦包含通配符，自动关闭凭证传递
- **密钥管理**：`.env` 不入版本库，提供 `.env.example` 模板，启动时校验密钥强度

### 4.7 关键技术五：积分台账的幂等设计

积分是最容易出错的模块——重复提交、并发请求都可能导致重复发分。本项目采用**不可变审计账本**模式：

- 每次积分变动是一条不可修改的 `PointTransaction` 记录，流水内固化规则版本、中文说明与业务元数据
- 表级唯一约束 `(user_id, module, event_type, source_id)` 保证同一来源只发一次，终态记录释放唯一键
- 嵌套事务兜底并发双写
- 对账自检：把各模块流水合计为账本总额，与用户表上的总积分比对，不一致时在接口层标记 `is_reconciled=false`；迁移前的历史余额单列展示，不与新流水混算

## 六、项目原创性与迭代说明

### 6.1 原创性声明

本项目为团队**独立原创开发**，未基于任何现有开源项目二次开发。代码结构、业务逻辑、提示词设计、测试用例均由团队成员编写。

项目中使用的第三方资源包括：

- 开源框架与库（Vue、FastAPI、SQLAlchemy 等），遵循各自开源协议
- 公开的历史图片素材（用于党史沉浸式场景），版权归原作者所有
- AI 艺术化复原插图

### 6.2 从原型到当前版本的迭代过程

项目经过多轮迭代，主要演进如下：

| 迭代方向 | 具体改进 |
|----------|----------|
| **AI 输出可靠性** | 早期直接展示模型返回的分数；后引入白盒校验层，对分数、置信度、证据长度做钳制，并拒绝将布尔值按数值处理 |
| **长上下文处理** | 辩论长对话曾导致提示词超长、响应缓慢；后增加 `DEBATE_HISTORY_MAX_CHARS` 等配置，对历史、陈词、证据分别设上界，超长部分显式标注"[内容过长，以下已截断]" |
| **JSON 容错** | 模型偶尔返回非 JSON 或截断 JSON；后增加容错解析、单次重试与纯文本回退三级策略 |
| **RAG 引用可信度** | 早期回答无引用；后引入逐句引用编号、引用重排去重、无证据拒答 |
| **积分幂等** | 早期重复提交会重复发分；后改为不可变台账 + 表级唯一约束 |
| **工程化规范** | 早期无静态检查；后引入 Ruff、Prettier、EditorConfig、GitHub Actions 与 32 项自动化测试 |
| **代码结构** | 清理未使用导入、展开压缩的单行语句、补充模块文档字符串、移除已弃用的 `on_event` 启动钩子，改用 FastAPI lifespan |
